### 이번 주 변화
- 프레임워크 코드 분석(#54)으로 방법마다 무엇이 공통이고 무엇이 다른지에 대해 분석함.

- dinomaly도 config 그대로(total_iter=5000) bottle 하나를 실측해 소요 시간을 확정함(128 epoch, 2.998 s/it) — MVTec+VisA 합계 약 112.7시간. VisA(12개)가 MVTec(15개)보다 짧게 나오는데, total_iter가 카테고리 크기와 무관하게 고정이라 합계가 카테고리 개수에 비례하기 때문. 공식 구현(8GB 노트북, 18시간 4분/13개)보다 3배 가까이 느림(5절 실험 1).

## 1. 서론

### 1.1~1.2 연구 배경, 기존 접근과 한계 (요약, W27~W39 반복 부분 축약)
- MVTec-AD·VisA 기준 산업 이상탐지(IAD) 연구. PatchCore(memory-bank 비교)를 기준으로 grid(H3)·transistor(H4)에서의 약점을 원인 가설로 두고 GLAD·Dinomaly·SimpleNet·RD·WinCLIP까지 재현·비교를 마쳤음(W27~W39).

### 1.3 우리가 집중하는 접근과 남은 문제
- 이번 주부터는 개별 방법을 각자 코드로 재현하는 대신, 교수자가 제공하는 **공통 프레임워크** 하나로 여러 방법(PatchCore·PadIM·WinCLIP·PromptAD·CoAD·UniAD·GLAD류·RD·RD-orig·Dinomaly·GLASS)을 같은 전처리·평가 코드에서 돌리는 방식으로 전환함.
- 남은 문제: 방법마다 config가 정한 학습량(예: RD 300 epoch, RD-orig 40 epoch, glass 640 epoch)이 크게 달라 실행 비용이 방법별로 수십~수백 배 차이 나고, 8GB 노트북과 12GB 데스크톱 중 어디서 돌릴지도 방법별 VRAM 요구량에 따라 갈림(5절 실험 1, README 5절 기기 분담표).

## 2. 사전 지식과 문제 정의

### 기술 용어
- *공통 프레임워크*: 이 브리프에서는 `experiment.yaml`의 `method`/`dataset`/`category`/`data_path` 네 값만 바꿔 여러 이상탐지 방법을 같은 전처리·데이터로딩·평가 코드로 실행하는 코드베이스(`dinomaly_share_codebase`)를 뜻함.
- *peak VRAM*: job 실행 중 `nvidia-smi`를 일정 간격(2초)으로 조회해 얻은 GPU 메모리 사용량의 최댓값. 기기 분담(노트북 8GB vs 데스크톱 12GB) 판단에 씀.
- *백본 가중치 V1 / V2*: PyTorch의 이미지 모델 라이브러리(torchvision)가 WideResNet50에 제공하는 ImageNet 사전학습 가중치 두 가지. 모델 구조는 같고 학습된 값만 다르다.
  - **V1**(`IMAGENET1K_V1`): 원래 제공되던 가중치. 원 논문(Wide ResNet)의 학습 방식을 재현했고 ImageNet 분류 정확도 78.5%. 예전 방식인 `pretrained=True`로 불러오면 이것이 선택된다. SimpleNet 공식 코드가 이 방식을 쓴다.
  - **V2**(`IMAGENET1K_V2`): torchvision이 개선된 학습 방식으로 다시 학습해 추가한 가중치. 정확도 81.6%. `weights="DEFAULT"`로 불러오면 이것이 선택되며, 공통 프레임워크가 이 방식을 쓴다.
  - 정확도는 torchvision이 가중치와 함께 제공하는 정보에서 확인함.

## 5. 실험

### 비교 기준
- glass·dinomaly처럼 config 학습량이 큰 방법은 실측 카테고리당 시간을 전체 카테고리·데이터셋으로 확장해, config 그대로 실행할 때의 소요 시간을 추정(실험 1).
- simple은 프레임워크 실행 결과를 SimpleNet 공식 코드(W39 재현)와 비교하고, 한 번에 한 가지 조건만 바꿔 원인을 좁힘(실험 2).

### 평가 지표
- I-AUROC / P-AUROC(class-separated, MVTec+VisA 15/12개 카테고리 평균). 실행 비용은 wall time(총 실행 시간)과 peak VRAM.

### 데이터셋
- MVTec-AD 15개 카테고리, VisA 12개 카테고리(공식 `split_csv/1cls.csv` 기준으로 MVTec 디렉터리 구조로 변환). sample unit: 이미지 1장. split: 공식 train(정상만)/test(정상+불량).

### 실험 1: dinomaly·glass 실행 소요 시간 추정

#### 질문
- 프레임워크의 모든 방법을 config가 정한 학습량 그대로 MVTec+VisA 전체에 실행하면 시간이 얼마나 걸리는가?

#### 가설
- H: 방법별 config 학습량 차이가 크면(glass는 meta_epochs=640으로 dinomaly의 total_iter 5000보다 카테고리당 훨씬 오래 걸림) 이번 주 안에 실행을 마칠 수 있는지가 달라진다.

#### 설정
- dinomaly(total_iter=5000): 처음엔 200 iter·600 iter 두 지점으로 선형 추정하려 했으나, 600 iter 쪽이 제한시간(1800초)에 걸려 잘린 값이라 무효였다. 대신 bottle 1개를 config 그대로(total_iter=5000, 총 385 epoch) 돌리다가 속도가 안정된 128 epoch 지점에서 멈추고, 그 구간의 실측 속도(2.998 s/iteration)로 카테고리당 시간을 구해 카테고리 수를 곱했다.
- glass(meta_epochs=640): bottle을 5 epoch 실행해 epoch당 시간을 재고, 여기에 config epoch 수(640)와 카테고리 수를 곱해 추정.
- 근거 경로: `dino5000_probe/run_logs/dinomaly__mvtec__bottle.log`(dinomaly), `lg_results/epoch_test_glass.csv`(glass).

#### 기대 결과
- 추정 시간이 이번 주(9/28 마감) 안에 끝나는 범위인지 확인.

#### 실제 결과
| 방법 | config 설정 | MVTec-15 | VisA-12 | 합계 | Raw Path |
|---|---|---|---|---|---|
| dinomaly | total_iter 5000 | 62.6h | 50.1h | **112.7h** | `dino5000_probe/run_logs/dinomaly__mvtec__bottle.log` |
| glass | meta_epochs 640 | 132.7h | 315.2h | **447.9h** | `lg_results/epoch_test_glass.csv` |

dinomaly 값은 bottle의 128 epoch 실측(2.998 s/it, 표본 128) 기준이다. `total_iter`가 카테고리 크기와 무관하게 고정이라, VisA(12개)가 MVTec(15개)보다 합계가 작다 — 오타가 아니라 합계가 거의 카테고리 개수에만 비례하기 때문이다. 128~146 epoch 구간(3.39 s/it, 표본 18)까지 반영한 상한은 MVTec 70.6h·VisA 56.5h·합계 127.1h. 끝까지 돌리지 않아서 config 설정에서의 I-AUROC/P-AUROC는 아직 없다 — 시간만 실측된 것이다. 공식 Dinomaly 구현은 같은 설정으로 8GB 노트북에서 13개 카테고리를 18시간 4분에 끝냈는데(W39 재현), 이 프레임워크 실측은 그보다 3배 가까이 느리다. 다만 하드웨어가 반대 방향(공식 구현 8GB 노트북, 이 실측 12GB 데스크톱)이라 그 차이를 하드웨어 탓으로 볼 수 없다. peak VRAM은 11,746 MiB로 8GB 노트북에서는 못 돌리고 데스크톱 전용이다.

glass 값은 bottle 5 epoch 실측(40.11/37.95/41.58/36.79/36.98초) 평균에 `configs/glass.yaml`의 `eval_epochs: 1`로 매 epoch 도는 평가 시간(약 5.7초/epoch)까지 더한 것이다. 평가를 뺀 학습 시간만이면 MVTec 115.6h·VisA 274.5h·합계 390.1h.

#### 해석
- glass는 config 그대로 두 데이터셋을 다 돌리면 약 18.7일(447.9h)이 걸릴 것으로 추정돼, 너무 오래 걸려 이번 주 마감(#55, 9/28)까지는 실행하지 못함. dinomaly(112.7h, 4.7일)도 이번 주 안에는 못 끝내 config 그대로는 미실행으로 남김(README 4절). 둘 다 이번 주 실행 대상에서 제외함 — dinomaly 112.7h에 남은 rd VisA(약 52h)까지 더하면 데스크톱 한 대로는 10/5경까지 걸린다. 학습량을 줄여서라도 포함할지는 다음 판단(8절 후보).

### 실험 2: simple 판별기가 학습되지 않은 원인

#### 질문
- 프레임워크로 실행한 simple이 왜 논문보다 크게 낮은가? (bottle I-AUROC 0.912 / P-AUROC 0.744, 논문 100.0 / 98.0, W39 공식 코드 재현 1.000 / 0.980)

#### 가설
- H: 학습 로그에서 판별기의 손실이 약 1.0에 멈추고 정답률이 0.0이었으므로, 판별기가 정상 특징과 가짜 이상 특징을 구분하지 못하고 있다. SimpleNet은 정상 특징에 표준편차 0.015의 노이즈를 더해 가짜 이상을 만드는데, 특징값의 크기가 공식 코드보다 크면 이 노이즈가 상대적으로 너무 작아져 둘이 구분되지 않는다.

#### 설정
- 같은 입력을 V1·V2 가중치의 백본에 넣어 특징값 크기를 비교함.
- 백본 가중치만 V1으로 바꿔 프레임워크 simple을 bottle에서 2 epoch 실행함(원인 확인용).
- 다른 후보(이미지 캐시, 라이브러리 버전, adaptor 학습률)를 하나씩 바꿔 실행해 배제함.
- 근거 경로: `related_work/source/W40_method_runs/result/README.md` 3-5절.

#### 기대 결과
- 가설이 맞다면 프레임워크 특징값이 공식 코드보다 크고, 가중치를 V1으로 바꾸면 판별기가 학습되어야 함.

#### 실제 결과
- 백본 로드 방식: 프레임워크는 `wide_resnet50_2(weights="DEFAULT")`로 불러오며 torchvision에서 이는 ImageNet **V2** 가중치다. 공식 코드는 `pretrained=True`, 즉 **V1**이다. 같은 입력에서 V2의 layer3 특징 표준편차는 0.85로 V1(0.09)의 약 9배다.

| 조건 (bottle) | 판별기 학습 | I-AUROC / P-AUROC |
|---|---|---|
| 프레임워크 그대로 (V2 가중치, 40 epoch) | 안 됨 (정답률* 0.0) | 0.9119 / 0.7439 |
| 가중치만 V1으로 교체 (2 epoch, 원인 확인용) | 됨 (정답률* 0.79) | 0.9929 / 0.9676 |
| SimpleNet 공식 코드 (V1 가중치, 40 epoch) | 됨 (정답률* 0.99) | 1.0000 / 0.9800 |

\* 정답률: 판별기는 특징마다 점수를 내며, 정상은 높게·가짜 이상은 낮게 내도록 학습한다. 여기서 정답률은 정상 특징 중 점수가 +0.5 이상인 비율과 가짜 이상 특징 중 점수가 −0.5 미만인 비율이다(±0.5는 SimpleNet이 정한 기준선, 학습 로그의 `p_true`·`p_fake`). 두 비율은 거의 같아 하나만 적었다. 학습되면 1에 가까워지고, 0이면 모든 특징이 0 근처 점수를 받아 정상과 가짜 이상을 구분하지 못한다는 뜻이다. 프레임워크 그대로 실행했을 때는 손실도 40 epoch 내내 약 1.0에 머물렀는데, 이는 모든 점수가 0일 때의 손실값(정상 쪽 0.5 + 가짜 이상 쪽 0.5)과 같다.

| 배제한 후보 | 확인 방법 | 결과 |
|---|---|---|
| 이미지 캐시 | 캐시를 끄고 실행 | 판별기가 똑같이 학습되지 않음 |
| 라이브러리 버전 | W39 공식 코드 재현 환경과 torch 버전(2.11.0)이 같음 | 공식 코드는 같은 버전에서 정상 학습됨 |
| adaptor 학습률(프레임워크가 공식보다 100배 작음) | 학습률만 공식 값으로 바꿔 bottle·cable·capsule 40 epoch 실행 | 세 카테고리 모두 판별기가 학습되지 않음 |

- 같은 백본 로더를 쓰는 patchcore도 V1으로 MVTec 15개를 다시 실행함: 평균 V2 0.9834 / 0.9796, V1 0.9826 / 0.9808로 거의 같음.
- simple V1 전체 결과(MVTec 15개): (실행 중, 완료 후 기재)

#### 해석
- 지지. 원인은 백본 가중치 버전이다. simple은 가짜 이상을 만드는 노이즈 크기가 특징값 크기에 맞춰 고정돼 있어, 가중치 버전이 바뀌면 학습 자체가 무너진다. 반면 patchcore처럼 특징 사이 거리로 판단하는 방법은 평균 성능이 거의 변하지 않았다.
- 그래서 simple만 V1으로 다시 실행해 보고한다. patchcore는 V1으로도 대조 실행했지만 결과가 거의 같아, 프레임워크 기본값(V2)으로 그대로 보고한다.

## 8. 이번 주 주요 질문 1개
- 질문: glass·dinomaly처럼 config가 정한 학습량 그대로는 실행에 매우 오래 걸리는 방법을, 학습량을 줄여서라도 포함해야 하는가, 아니면 비교에서 제외해야 하는가?

- 왜 이 판단이 틀렸을 수 있는가: 프레임워크 안에서 설정한 config 값이 공식 코드와 다를 수 있기 때문임.
